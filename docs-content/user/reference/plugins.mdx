# 🔌 Plugins

A **plugin** is a piece of middleware that runs as a step in a rule's pipeline. Plugins can transform the outgoing request, transform the incoming response, or both — they're how the gateway handles format conversion, header injection, and content fixes without forcing you to write a line of code.

This page is a **quick-reference landing**. The canonical authoring docs live under [Rules](rules), where you compose plugins into pipelines. The full plugin catalog also appears in the **Available Plugins** section of the Rules page (read-only).

## 🗂️ Categories

Plugins fall into a handful of rough categories:

### 🔁 Format Converters

Request → translate between OpenAI, OpenAI Responses, Anthropic Messages, and Google Gemini.

| Plugin ID | Direction |
|---|---|
| `openai2anthropic` | OpenAI Chat Completions → Anthropic Messages |
| `anthropic2openai` | Anthropic Messages → OpenAI Chat Completions |
| `openai2responses` | OpenAI Chat Completions → OpenAI Responses |
| `responses2openai` | OpenAI Responses → OpenAI Chat Completions |
| `openai2gemini` | OpenAI Chat Completions → Google Gemini |
| `gemini2openai` | Google Gemini → OpenAI Chat Completions |
| `anthropic2responses` | Anthropic Messages → OpenAI Responses |
| `responses2anthropic` | OpenAI Responses → Anthropic Messages |
| `anthropic2gemini` | Anthropic Messages → Google Gemini |
| `gemini2anthropic` | Google Gemini → Anthropic Messages |

> **Note:** You rarely need to add these manually — the gateway's **auto-translation** inserts the right format converter into the pipeline when the request format doesn't match the provider's declared format. Add a converter only when auto-translation isn't enough or you need stricter control.

### 🪪 Header Injection

| Plugin ID | Description |
|---|---|
| `custom_header` | Inject fixed key/value `Authorization` or other headers into the outbound request — useful for routing scenarios where the provider expects an internal token |

### 🖼️ Image Fixes

| Plugin ID | Description |
|---|---|
| `fix_anthropic_images` | Workaround for image-reading quirks in certain Claude Code + llama.cpp combinations (see [llama.cpp PR #22536](https://github.com/ggml-org/llama.cpp/pull/22536)) |
| `fix_openai_images` | Normalize image URLs that some upstreams reject |

### 🛠️ Operational Plugins

| Plugin ID | Description |
|---|---|
| `request_logger` | Logs the full request body at debug level — pair with **Payload Capture** in Settings to make it actually visible in the inspector |
| `response_logger` | Same idea, but for the response |
| `usage_extractor` | Pulls token-usage fields out of the response so they show up in the Logs tab |

## 🔍 Where Plugin IDs Come From

The catalog comes from the gateway itself. Every time you open a Rule form, the dropdown is populated from the live response. Plugins installed on the gateway (third-party plugins, custom builds) appear automatically without an app update.

If you don't see a plugin you're expecting:

1. ✅ Confirm the gateway is connected (the green dot in the sidebar header)
2. 🔄 Click the refresh button on the Rules page
3. 📦 Check the gateway's plugin directory if it's a third-party plugin

## ✏️ Authoring

Plugins are added in the **Rule form → Pipeline Configuration** section:

1. ➕ Click **Add Step** to append a new step card
2. 🛠️ Pick a plugin from the dropdown
3. ⚙️ Fill in the automatically-generated options form
4. 🔃 Reorder with the up/down controls (or the drag handle if present)
5. 💾 Save the rule

See [Rules](rules) for the full walkthrough of the form, including how multiple steps concatenate and how priority is determined.

## 🧪 Verifying Behaviour

The best way to confirm a plugin is wired correctly is to inspect the live request:

1. ⚙️ Enable **Settings → Payload Capture**
2. 📡 Send a request through the gateway
3. 📺 Open the **Logs** tab and click the resulting row
4. 🔬 Compare the **Parsed** view to the raw payload — the plugin's effect should be visible

See [Logs](logs) for the inspector UI in detail.
